## 2. Соответствие Курсовому проекту (КП)

### Что совпадает с текстом КП
- Полная ER-модель из 10 таблиц реализована миграциями 1:1.
- Связи (1:M, M:N через `car_option`, 1:1 `orders — credit_applications`) совпадают.
- Контроллеры и логика из листингов КП (6–12) соответствуют фактическому коду.
- Оформление заказа в транзакции, аннуитетный расчёт кредита, возврат авто в `available` при отклонении сделки — как описано.
- UI-компоненты Blade (Input, Select, Checkbox...) — вынесены в представления `components`, Из КП упомянуты Input/Checkbox.

### Расхождения с КП
- В КП заявлена модель/компонент **Checkbox** — в коде компонента `checkbox` фактически нет (опции выведены нативно в `_form` и модалке). Компоненты Select/Alert/Money/CarStatus/SpecText есть, но в листингах КП не описаны.
- КП не упоминает ведение «истории поиска», хотя в постановке задач это фигурирует.
- В модели User поле именовано `tel`, в реальной БД колонка называется `phone` (рассинхрон между кодом и схемой БД на конкретной машине).

## 3. Недостатки реализации (критичные)

### 3.1. Разделение прав доступа отсутствует
- Админ-маршруты `/admin/**` защищены только `auth`, но **не проверяют `is_admin`**. Любой авторизованный клиент технически может открыть админ-панель и управлять авто. На страницах кнопка скрывается через `@if(Auth::user()->is_admin)`, но серверной защиты нет.
- Решение: middleware `is_admin` + проверка в контроллере/роуте.

### 3.2. Статусы сделок не соответствуют ТЗ
- По ТЗ и КП требуется 5 этапов: «Заявка оформлена», «Договор подписан», «Предоплата внесена», «Автомобиль выдан», «Сделка закрыта».
- Фактически в БД ENUM `orders.status` содержит только `created | confirmed | rejected`.
- Решение: расширить ENUM и логику переходов.

### 3.3. Нет управления текстовым контентом из админки
- ТЗ прямо требует редактирование описаний/текстов без вмешательства в код. Тексты зашиты в Blade. CMS-модуль контента не реализован.

### 3.4. История поиска не реализована
- Заявлена в постановке задач КП (сохранение истории поиска клиента). Отсутствует.

### 3.5. Отсутствие «оформления договора» как сущности
- Есть статусы и заказы, но отдельной сущности/документа «договор купли-продажи» нет. Для полноты ТЗ нужна таблица `contracts` или расширение `orders`.

### 3.6. Итоговый «финансовый отчёт» примитивен
- Выводится только сумма и кол-во подтверждённых заказов. Нет разбивки по периодам, месяцам, маркам, типам оплаты, экспорта. Для защиты стоит расширить.

## 4. Недостатки (технические / качество кода)

### 4.1. Схема БД и код рассинхронизированы
- В миграции `users` колонка называется `tel`, но в реальной БД (на машине разработки) — `phone`. При развёртывании на чистой БД это приведёт к ошибкам (пользователь это уже видел при `db:seed`). Нужно привести в соответствие.

### 4.2. `@method('POST')` в форме edit — избыточно
- Форма и маршрут обновления — оба POST. Лишний `@method('POST')` в шаблоне `edit.blade.php` не ошибка, но путает.

### 4.3. Неиспользуемый `use Storage` и порядок импортов
- `use Illuminate\Support\Facades\Storage` в AdminController используется; но в некоторых местах класс вызывается с FQN (`\Illuminate\Support\Facades\Storage::url`), что непоследовательно.

### 4.4. Магия в blade (inline JS, повторный CSS)
- Инлайн-JS в представлениях (каскад моделей, пересчёт кредита, удаление фото) дублирует друг друга и часть логики живёт и в `.php`, и в `.js`. Стоит вынести в модули и данные — в `data-*`.

### 4.5. Нет обработки ошибок на стороне клиента единообразно
- Валидация разбросана: часть в контроллерах (сервер), часть inline-JS (клиент), без единого компонента `validation-errors` на часть форм.

### 4.6. Потенциальная проблема удаления изображений
- При удалении обложки/последнего подходящего фото через `imageDestroy` проверка «минимум 2 фото» на удаление **не накладывается** (только при создании/редактировании), что противоречит правилу «от 2 картинок».

### 4.7. Кредитный расчёт не защищён от пересчёта на стороне клиента
- `interest_rate`, срок и `down_payment` приходят из формы и проходят валидацию диапазонов, но сервер повторно **не пересчитывает** месячный платёж от проверенной суммы, если клиент подменит скрытое поле `final_price` (впрочем, `final_price` заказа считается сервером от `car->price + options`, что корректно).

## 5. Оценка полноты (ваша шкала)

| Блок | Полнота |
|---|---|
| База данных (ER → реляционная, нормализация) | 90 % |
| Авторизация / роли | 60 % (нет серверного разграничения admin) |
| Главная страница | 70 % (нет отзывов) |
| Каталог + фильтрация | 90 % |
| Карточка авто + галерея | 95 % |
| Резервирование + опции + кредит | 90 % |
| Личный кабинет | 80 % |
| Админ-панель (CRM) | 85 % |
| Управление контентом из админки | 0 % |
| История поиска | 0 % |
| Договоры | 0 % |
| Финансовый отчёт | 50 % |

**Общая оценка: ~ 75 % соответствия.**
Работоспособный, целостный прототип с полной БД и основным функционалом, но не дотягивает до полного ТЗ: не хватает ролевого ограничения, редактирования контента, истории поиска, полного цикла «договор» и развитой отчётности.

## 6. Приоритетный план доработки

1. Создать middleware/проверку `is_admin` для всех `/admin/*` (критично — безопасность).
2. Расширить статусы сделок до 5 этапов по ТЗ (миграция + ENUM + UI).
3. Добавить управление контентом (модель `page_contents` или `settings` + CRUD в админке).
4. Реализовать сохранение истории поиска клиента.
5. Привести схему БД и код к единообразию (`tel`/`phone`).
6. Накладывать правило «минимум 2 фото» и на удаление.
7. Расширить финансовый отчёт (периоды, экспорт).
